# Pre-registration J — validity protocol for the Continuum mouse channel (Phases P0–P6)

Written and frozen on 2026-09-15, **before any Phase P0–P9 code has run**, after the owner agreed to
the plan in `paper/pages/mouse-validity-protocol.html`. Its SHA-256 and that of `SPLIT_J.json` are
recorded in `PREREGISTRATION_J.sha256` and in every result file of these phases; the analysis refuses a
result produced under other hashes. Nothing in this file changes after any lockbox result exists.

## 1. Scope

* Confirmatory here: P0 (lockbox and baseline), P1 (sample order and threshold method), P2 (operating
  point and decision rule), P3 (enrolment amount), P4 (enrolment quality), P5 (threshold floor),
  P6 (single lockbox evaluation).
* Registered separately, later: P7 (diagnosis of the owner's live data, step sizes |dx|, |dy| only),
  P8 (user study: real use, days, same-device impostors, verified adaptation), P9 (longer windows).
  **P8 does not start until the university's ethics/approval requirement is confirmed.** P9 does not
  start until P6 is complete.
* Experiments A–I and all later analyses on the development users are **development results**. None of
  them is a final result; P6 is the only final test.

## 2. Data split (SPLIT_J.json, generated by `services/model-api/make_split_j.py`)

SapiMouse, 120 users, two sessions each (3 min, 1 min), same day.

* **Development (20)**: the held-out users of Experiments A–I (`artifacts/mouse-ws50-aligned/holdout_users.json`):
  user1, user8, user9, user16, user19, user29, user69, user70, user85, user86, user89, user91, user98,
  user101, user104, user107, user108, user111, user115, user119. user98 (324 enrolment windows) serves
  as an impostor only, as before; 19 are targets.
* **Lockbox, untouched final test (20)**: drawn with `numpy.random.default_rng(20260915)` from the base
  users meeting an eligibility rule fixed before counting (>= 440 A5 windows in the 3-min session,
  >= 150 in the 1-min session; volume only, never a score). 80 base users were eligible. Drawn:
  user6, user18, user24, user32, user34, user42, user45, user46, user52, user60, user61, user63, user64,
  user73, user78, user90, user92, user93, user95, user103.
* **Base training (80)**: every other user (listed in SPLIT_J.json). They are the only source of base
  training windows, of the scaler, and of personal-model negatives.

No lockbox user's data is read by any P0–P5 step except P0's construction of the split and the base
(from which they are excluded). No development or lockbox user enters base training or negatives.

## 3. Held fixed throughout P0–P6

* Representation A5 (|dx|, |dy| in px per step), 50-step windows, stride 10, deployed step filter
  (idle split 0.5 s, zero-displacement moves dropped except clicks, minimum path 0.08 × 1920).
* Base: SapiMouse FCN (arch B6) trained by `train_mouse_fcn.py` with its defaults (seed 101, up to 40
  epochs, its early stopping, temporal 80/20 split of each base user's 3-min session), with `--holdout`
  listing the 40 development + lockbox users, output `artifacts/mouse-fcn-a5-j80`, negatives file
  `data/mouse_only/Mouse_A5_W50_base80.h5` (base-training users only).
* Personal model: model-api `train_user_payload` unchanged (frozen conv1+bn1, binary head, Adam 3e-4,
  15 epochs, batch 32, early stopping patience 6, train seed 7, negatives 2 × positives drawn with seed
  21 from the base-80 negatives file), except the validation scheme where a threshold method in P1
  defines it.
* Samples: an enrolment of E windows (the first E windows of the 3-min session) is divided into
  consecutive 55-window samples. Because consecutive windows share steps, whenever windows are held out
  (for validation or for scoring) while others train, the **4 windows on each side of every boundary**
  between held-out and training windows are removed from training ("boundary purge"). Five windows
  apart share no step, so this makes held-out samples as separate as real, separately recorded samples.

## 4. Evaluation units

* Genuine stream: the target's 1-min session. Development: calibration half = first half of the
  stream, test half = second half, with impostor identities alternating between halves (as in A–I).
  Lockbox: the whole 1-min session; impostors are all other lockbox users.
* Impostor run: the first 150 windows (~40 s) of another user's 1-min session, one contiguous run per
  identity (shorter if the session is shorter). Development impostors are development users only;
  lockbox impostors are lockbox users only.
* **Live-cadence replay**: a decision is taken after every 6 new windows (one check, ~1.6 s at 0.269 s
  per window); the rule is evaluated on the last N windows; after a prompt the buffer empties and the
  next decision needs N new windows. The every-window cadence of Experiment I is reported as a secondary.

## 5. Objective and metrics

**Primary system objective (owner-agreed)**: among operating points whose mean genuine false passkey
prompts per minute of movement is **<= 0.2**, the one that **catches the largest share of impostor
runs** (a run is caught if it draws at least one prompt); ties by shorter median time to catch, then
smaller N, then lower percentile. If no point meets 0.2, the budget relaxes to 0.5, then 1.0 (reported).

Always reported beside it, per user and summarised by mean, median, IQR and range: per-window AUC, EER,
TAR@FAR=1%; genuine prompts per minute; share of users never prompted; genuine interruption rate
(share of decisions that prompt); impostor runs caught and never caught; median time to catch; the full
trade-off curve (prompts per minute vs runs caught). No user is removed from any result.

## 6. Phases

### P0 — Lockbox and baseline
Build the base-80 model and negatives (section 3). Re-measure the current system (S0 = Method A,
1st percentile, vote 30 of 60, E = 330) on the development users with the base-80 model; this is a
development sanity report and decides nothing.

### P1 — Sample order and threshold method
* Enrolment E = 330 (six samples). Orders: the identity, the five other rotations (each sample last
  once), and four permutations from `default_rng(20260916)` distinct from the rotations: 10 orders.
* **A** (current): windows in the given order; model-api's contiguous validation tail (20%, gap 5) with
  boundary purge; threshold = percentile q of the model's scores on all E enrolment windows.
* **B** (leave-one-sample-out): for each sample k, train on the other samples (boundary purge), score
  sample k; threshold = percentile q of the pooled out-of-sample scores; the deployed model is trained on
  all samples. In every fold and in the final model, early stopping uses the last 11 windows of every
  training sample (boundary purge), so no sample is special.
* **C** (grouped 3-fold): as B with folds = sample pairs {1,2}, {3,4}, {5,6} in the given order.
* Each method gets its operating point by the section-5 objective on the development calibration
  halves (q in {1, 2, 5, 10, 15, 20, 30, 40, 50}; vote k of N with k from ceil(N/2) to N, mean, median;
  N in {20, 40, 60}; live cadence), for the identity order; the point is then held fixed across orders.
* Measured on development test halves for every order: threshold, enrolment score distribution,
  **genuine low-window rate** (share of the target's genuine windows below its threshold), genuine
  prompts per minute, runs caught, time to catch, per-window AUC/EER/TAR.
* **Does order matter (reported conclusion, Method A)**: yes if, for at least 25% of targets, the
  within-user range across the 10 orders exceeds 0.10 in threshold, 10 points in genuine low-window rate,
  or 0.5 in genuine prompts per minute.
* **Adoption** (Holm over the B-vs-A and C-vs-A families): a method replaces A if (i) the per-user SD
  across orders of the genuine low-window rate is significantly lower than A's (prompts per minute is
  too coarse per user for this test and is reported only), and (ii) its runs caught
  is non-inferior (lower 95% bound of the difference >= −5 points) and its prompts per minute is not
  higher by more than 0.1 (upper 95% bound). If both B and C qualify, C is chosen when its runs caught is
  within 2 points of B's (point estimate), else B. If neither qualifies, A is kept.

### P2 — Operating point and decision rule
With the P1 method, the section-5 search is re-run on the development calibration halves (identity
order) and frozen. Reported on development test halves.

### P3 — Minimum sufficient enrolment
Budgets E = 55, 110, 165, 220, 275, 330, 385, 440 (1–8 samples), 19 development targets, P1 method and
P2 point fixed. Budgets the method cannot support (B needs >= 2 samples, C >= 3) are reported with A for
reference and cannot be selected. Threshold stability = within-user SD of the threshold over the
identity order and two rotations. **Selection**: the smallest budget whose differences to E = 440 on
development test halves have runs caught lower bound >= −5 points, per-window AUC lower bound >= −0.02,
and prompts per minute upper bound <= +0.1. If the selected budget is not 330, P2's search is re-run at
that budget before freezing.

### P4 — Enrolment quality
Candidates fixed now: mean window path length; median step magnitude; share of steps in drags; idle
splits per 100 steps; share of exact-duplicate windows; share of windows rejected by the minimum-path
rule in the enrolment span; step-size IQR. For each development target, 10 enrolments of E windows from
evenly spaced offsets of the 3-min session, each trained with the P1–P3 method. Within-user Spearman
correlation between each candidate and each outcome (genuine prompts per minute, runs caught, AUC),
averaged over users; bootstrap over users; Holm over the 21 tests. If none survives: no quality gate.
If one survives, the gate itself is specified in an amendment before P6 and validated only on the lockbox.

### P5 — Threshold floor
Spearman correlation between per-user threshold and per-user runs caught (P1–P4 system, development
test halves). Only if its 95% lower bound is > 0: floor candidates = the 5th to 50th percentiles (step 5)
of the development thresholds; the floor applied as max(threshold, floor) is chosen by the section-5
objective on development calibration halves. Otherwise: no floor.

### P6 — Single lockbox evaluation
S0 (current system, base-80) and S1 (P1–P5 choices) are frozen, then evaluated **once** on the 20
lockbox users (enrolment = the first E windows of the 3-min session; genuine = whole 1-min session;
impostors = all other lockbox users), live cadence. Confirmatory family (Holm over two): genuine prompts
per minute (S1 − S0) and runs caught (S1 − S0). **S1 is declared better** if prompts per minute is not
higher by more than 0.1 (upper bound) and runs caught is not lower by more than 5 points (lower bound),
and at least one of the two improves significantly. Otherwise S0 stands. Per-window AUC/EER/TAR, time to
catch and per-user tables are reported for both. Balabit (10 users; training sessions as enrolment,
labelled test sessions as genuine/impostor; base-80, no Balabit training) is an external report only.

## 7. Statistics

Paired bootstrap over users, 10,000 resamples, seed 17, two-sided p = 2 × min tail share; 95% percentile
intervals; Holm within each phase's confirmatory family; effect size = mean paired difference with its
interval and the share of users improved. "Numerically better" and "statistically supported" are always
reported separately. Twenty users resolve about 0.04 AUC; per-user prompt rates are coarse (a
development test half is ~27 s); these limits are stated with every result.

## 8. Stopping, deviations, lockbox use

* A phase ends when its runs are complete; no phase stops early on results. Technical failures are
  re-run with identical settings and logged in RUN_LOG.md.
* A component whose adoption rule is not met keeps its current (S0) value.
* The lockbox is scored exactly once, after S1 is frozen and hashed. Any defect found afterwards is
  reported with both the original and the corrected result, as a deviation; S1 is not changed because of
  lockbox results.
* Not allowed at any point: changing the split, the objective, a margin or a rule after seeing results
  it would affect; removing users or sessions; choosing on lockbox data; reporting only favourable runs.
